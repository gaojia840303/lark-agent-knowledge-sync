# 项目背景

本项目来源于 AI 提效团队对“业务 Agent 如何持续获得可信、可用的关键知识”的讨论。项目定位不是“自动学习”，而是为业务 Agent 建设可治理的关键知识维护与供给能力。

现有业务 Agent 已经可以读取飞书知识并回答问题。对于已绑定知识库中的新增、修改和删除，平台是否会自动、及时更新 Agent 的检索结果，目前仍需通过实际测试确认。

项目同时处理三个问题：用一次性、限时黑盒测试确认知识库平台的绑定与索引边界；验证上游来源准入和运行成本是否可控；针对会议、Meegle、Base 和上游文档等知识库外部来源，建设一份全局维护、按 Agent 配置运行的知识维护 Skill。Phase 0 可与代码加固和 MVP 准备并行，但在结果明确前不得启用生产调度，也不得据此裁定链路 A 的最终责任。

公司每天在飞书中产生大量会议、妙记、文档和项目记录，因此本项目不建设企业内容全量扫描器。上游发现采用“主动投递和专用业务视图为主、受限增量扫描为辅”：个人工作文档默认排除，先使用元数据、变更记录和业务规则做低成本筛选，只对少量候选读取正文并调用模型提炼。

项目不建设新的问答检索链路，也不建设一个替代全部业务 Agent 的中央知识 Agent。每个 Agent 必须先明确角色、职责、决策范围、输出契约和成功指标，再决定允许哪些来源进入候选流程。如果三项知识库验证通过，正式知识库内部的普通人工编辑不进入同步 Skill。动态状态继续以 Base 和 Meegle 为权威来源；只有尚未进入目标知识库的稳定事实、决策、规则、流程和复盘结论才进入知识沉淀流程。多 Agent 共用同一来源时，后续采用一次采集、缓存复用、分别路由，避免重复读取和重复消耗 Token。

上位决策以 [项目契约](项目契约.md) 为准。详细架构与实施阶段见 [Agent 关键知识维护与供给能力落地方案](Agent自动更新能力落地方案.md)；验证方法见 [知识库绑定行为验证](知识库绑定行为验证.md)、[Agent 上游采集范围与成本验证](采集范围与成本验证.md) 和 [MVP 评测卡](MVP评测卡.md)。
