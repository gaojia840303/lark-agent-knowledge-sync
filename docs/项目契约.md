# Agent 关键知识维护与供给｜项目契约

> 生效日期：2026-07-28
> 状态：当前项目的上位执行基线

## 1. 项目定位

本项目建设一套按业务 Agent 角色运行的关键知识维护与供给能力：从明确授权的上游来源中发现与 Agent 职责相关的稳定知识变化，保留来源证据，经过权威性、范围、时效和人工审核后，写入该 Agent 的指定知识文档。

项目不是中央知识 Agent、公司内容全量扫描器或“自动学习”系统。公共代码只维护一份，每个业务 Agent 使用独立配置和独立审核状态。

## 2. 服务对象与业务结果

服务对象：持续使用稳定规则、正式决策、方法和复盘经验完成业务输出的 Agent 及其业务负责人。

期望结果：

- Agent 使用的关键规则和正式决策不过期、不串库、可追溯。
- 业务负责人能够看到变化从哪里来、为什么相关、谁批准、何时生效。
- 减少人工搬运和重复整理，同时不增加不可控的扫描、Token 与审核成本。
- 用 Agent 最终业务输出是否改善衡量价值，而不是只看抓取数量或节省 Token。

## 3. 单 Agent 准入条件

首个 MVP Agent 必须同时具备：

1. 清楚的角色、职责和决策范围。
2. 明确且可验收的输出契约与成功指标。
3. 业务负责人、来源负责人和审核人。
4. 可授权、范围固定的主动投递入口、专用视图或受限来源。
5. 公共与专属知识目标文档。
6. 不少于 10 条正例，并包含反例、边界、冲突或替代样例。

品牌六要素 Agent 只有满足上述条件时才作为默认候选；报店资料等实时查询和确定性文档生成能力不作为首选。

## 4. 能力边界

| 层级 | 本项目职责 |
|---|---|
| L0 来源层 | 维护来源准入、负责人、授权范围、变更证据和采集状态 |
| L1 正式知识 | 沉淀经审核的事实、规则和正式决策 |
| L3 经验知识 | 沉淀有案例结果支持、经过审核的复盘经验 |
| L2/L4 | 不负责完整语义平台或 Context 编译，只向下游提供治理后的知识、来源和关系 |

动态 Meegle/Base 状态继续在权威事实源中实时查询，不复制为长期知识。

## 5. 固定输出

每次运行只允许产生以下输出：

- 只读预演结果：范围、漏斗、预算消耗、预计提案和停止原因。
- 待审核提案：原文事实、候选正文、来源证据、相关性、准入方式和权威等级。
- 运行与游标记录：成功来源、失败来源、预算和幂等状态。
- 审核批准后的知识块：固定目标、同步标识、来源时间和内容哈希。

模型语义阶段接入前，候选正文仍是清洗后的来源摘录，不得表述为已完成事实/结论/推断提炼。

## 6. 明确不做

- 不扫描公司全部飞书内容或未经批准的个人文档。
- 不把读取权限自动解释为业务授权。
- 不重新扫描目标知识文档形成自循环。
- 不把动态状态沉淀成永久知识。
- 不在没有评测、预算和人工审核时自动写正式知识。
- 不由 Codex、Claude Cowork、WorkBuddy 各自维护一套分叉代码；Git 主仓库是唯一实现真相源。

## 7. 决策优先级

发生冲突时按以下顺序裁决：

1. Nicolas 等业务负责人的最新明确决定和公司宏观规划。
2. 会议原文、正式制度和已批准决策。
3. 当前 Git 主线代码、测试和真实运行证据。
4. WorkBuddy 的飞书权限、视图和现场运行证据。
5. Claude/Codex 的架构、语义和评测建议。

最新证据高于旧交接，明确决定高于模型推断，真实业务结果高于模型自评。

## 8. 当前推进门槛

- Phase 0 是一次性、限时的知识库绑定黑盒测试，可与代码加固和 MVP 准备并行；它只阻塞生产启用和链路 A 的职责裁决。
- Phase 0.5 使用 `scan --dry-run` 验证来源、漏斗和非模型预算，再用隔离审核仓验证提案质量。
- 语义模型只在配置契约、来源清单、安全硬限制和评测集准备完成后接入。
- 单 Agent 连续运行 2—3 个周期并达到评测门槛后，才进入生产调度、多 Agent 和共享采集缓存。
