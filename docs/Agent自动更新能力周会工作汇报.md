# Agent 自动更新能力｜周会工作汇报

> 汇报日期：2026-07-20  
> 当前阶段：单 Agent MVP 双前置验证  
> 一句话结论：基础同步和审核链路已经完成；下一步先验证知识库原生感知能力，再验证上游采集范围与成本，避免把公司海量飞书内容直接送入模型。

## 一、项目目标

建设一套供多个业务 Agent 共用、范围和成本可控的知识维护能力：

- 在每个 Agent 明确授权的高价值来源内，以主动投递和专用业务视图为主、受限增量扫描为辅，发现值得沉淀的信息。
- 先用元数据、变更记录和业务规则低成本筛选，只对少量候选读取正文并调用模型提炼。
- 经人工审核后，写入对应 Agent 的公共或专属知识目录。
- 每个 Agent 使用独立配置，共用一份 Skill，避免重复开发和知识串库。

本项目不扫描公司全部飞书内容，不默认扫描个人工作文档，不重做 Agent 的问答检索能力，也不复制 Meegle、Base 中持续变化的项目状态。

## 三、落地步骤

1. **Phase 0：验证知识库原生感知能力**  
   分别测试已绑定文档修改、绑定目录新增文档、文档删除或移出后，Agent 能否及时使用最新有效内容。

2. **Phase 0.5：验证采集范围与成本**  
   确定主动投递入口、专用业务视图、受限白名单和单次预算，验证个人文档不被默认扫描，模型只处理少量候选。

3. **Phase 1：单 Agent MVP**  
   在严格小范围内准备不少于 10 条预期样例，跑通“发现—筛选—审核—应用”，并连续运行两次验证不重复。

4. **Phase 2—3：多 Agent 与自动运行**  
   补齐元数据优先、硬预算、Token 统计、共享采集缓存和 `dry-run` 后，再扩展多 Agent 并上线自动运行。

## 四、预计卡点

| 卡点 | 可能影响 | 应对方式 |
|---|---|---|
| 知识库更新是否会自动生效尚未验证 | 无法准确判断 Skill 是否需要处理目标知识库内部变化 | 先完成三项黑盒测试，并明确可接受的生效时限 |
| 飞书内容量大且个人文档噪音高 | 全量筛查会造成 Token、权限和审核成本失控 | 默认不做全量扫描，个人文档默认拒绝，采用主动投递、专用视图和受限扫描 |
| 当前尚未实现元数据优先和总量硬预算 | 读取范围扩大后仍可能先取大量正文 | 首个 MVP 严格限小范围；扩大前补齐正文、候选、Token 和时长硬限制 |
| MVP 业务配置尚未齐备 | 无法进入真实数据验证 | 确认 Agent、负责人、审核人、数据源、目标目录和 10 条样例 |
| 上游来源与目标文档可能配置重叠 | 可能反复读取自己写入的内容，形成循环提案 | MVP 前人工校验，并补充代码级硬拦截 |
| 用户身份授权不适合长期自动运行 | Token 失效会导致定时任务中断 | 生产阶段改用应用身份或专用服务账号，并验证自动刷新 |
| 知识提炼准确率和审核工作量未知 | 提案过多或质量不稳会增加人工负担 | 先测候选漏斗和审核通过率，再接入真正的模型提炼，之后逐步放开低风险自动化 |

## 五、待解决问题

本周优先确认以下事项：

1. 用哪个 Agent、哪个知识目录完成三项绑定行为测试。
2. 知识新增或修改后，多长时间内生效算“可接受”。
3. 确定首个 Agent 的主动投递入口、专用视图、白名单来源和单次 Token/数量预算。
4. 三项测试和成本验证通过后，确定首个 MVP Agent；如品牌六要素和产品五张牌同时满足条件，默认选择品牌六要素 Agent。
5. 补齐真实来源、目标文档、负责人、审核人和不少于 10 条预期变更样例。
6. MVP 前完成来源与目标不重叠、文档搜索必须限定目录等代码级校验。

## 六、下一阶段完成标志

- 三项知识库绑定行为测试有明确结论，Skill 边界最终确认。
- 采集范围与成本验证通过，公司全空间、个人文档和目标知识的越界读取数为 0。
- 单 Agent MVP 配置准备完成，并成功生成首批真实知识提案。
- 不少于 10 条预期样例中至少发现 8 条，首轮“批准或仅需小修改”的提案不低于 60%。
- 相同内容连续运行两次不重复，且运行未超过批准的正文、候选、Token 和时长预算。
