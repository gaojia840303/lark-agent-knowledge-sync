# Agent 自动更新能力落地方案（修订版）

> 本次修订同时明确两项前置边界：先验证 Agent 已绑定知识库的原生感知能力；再验证上游采集范围和运行成本。项目不扫描公司全部飞书内容，不默认读取个人工作文档，模型只处理经过低成本筛选后的少量候选。

## 一、方案结论

本项目不建设一个独立的“知识更新 Agent”，而是建设一套供每个业务 Agent 使用的通用更新能力：

- 全局只维护一份 `lark-agent-knowledge-sync` Skill。
- Skill 与各 Agent 的其他业务 Skill 并列存在，不合并成一个巨大的 `SKILL.md`。
- 每个 Agent 使用自己的配置文件，定义数据源、关注范围、知识目录和审核人。
- Skill 的逻辑统一升级，Agent 间的差异通过配置解决，不复制修改公共代码。
- 飞书 Bot 已经可以读取飞书知识，因此本项目只负责维护知识，不重做问答检索链路。
- Meegle 是项目管理的核心事实源，正式纳入第一阶段能力范围。
- 本 Skill 不重复监控 Agent 已绑定知识库中的普通人工修改；是否能够自动感知这类变化，必须先通过新增、修改、删除三项验证。
- 验证通过后，Skill 只处理知识库外部的上游信息发现与知识沉淀；验证失败的问题作为知识库绑定或索引能力缺口单独处理。
- 上游知识发现采用“主动投递和专用业务视图为主、受限增量扫描为辅”，不以公司飞书空间作为默认扫描范围。
- 员工个人工作文档默认不扫描；只有主动提交、进入指定共享目录或被业务负责人明确配置的文档才能进入候选范围。
- 先用更新时间、目录、人员、项目、状态和内容哈希等低成本信息筛选，再读取必要正文；只有少量候选进入模型判断与知识提炼。

“全局 Skill”表示统一维护和发布，不表示由一个中央 Agent 代替所有 Agent 工作。实际运行链路为：

```text
主动投递、变更事件或定时任务
→ 指定一个 Agent 配置
→ 调用公共更新 Skill
→ 检查该 Agent 明确授权的高价值来源
→ 先做来源侧增量、元数据和规则筛选
→ 只读取少量候选正文并进行知识提炼
→ 写入 Base 审核表
→ 审核通过后更新该 Agent 对应的飞书知识目录
```

Codex Skill 是可复用工作流，不是持续在线的飞书 Bot 后端；自动运行仍需 Codex 自动化、CLI Runner 或在线执行器。参见 [Codex Skills 与自动化用例](https://developers.openai.com/codex/use-cases?category=automation)。

## 二、知识库与运行架构

### 2.1 飞书知识结构

采用“同一知识空间、公共与专属分目录”的结构：

```text
Agent 知识空间
├── 00-公共知识
│   ├── 品牌公共方法
│   ├── 产品公共方法
│   ├── 公司规则
│   └── 公共术语
└── 10-Agent专属知识
    ├── 品牌六要素-Agent
    ├── 产品五张牌-Agent
    └── 其他Agent
```

路由规则：

- 公司级规则、公共方法和跨 Agent 通用知识写入公共目录。
- 特定品牌、产品或 Agent 场景知识写入对应专属目录。
- 目标目录由配置文件确定，不允许模型自行选择其他目录。
- 飞书应用必须被添加为知识空间成员或文档协作者，才能读取和编辑相应内容。参见 [飞书知识库权限说明](https://open.feishu.cn/document/ukTMukTMukTM/uUDN04SN0QjL1QDN/wiki-overview)。

### 2.2 必须先验证的关键前提

Agent 连接知识库，只能说明它具备检索入口，不能直接证明它会自动、及时地感知知识库变化。正式启动知识同步 MVP 前，必须验证以下三点：

1. 修改已经绑定的文档后，Agent 能否在可接受时间内读取修改后的内容，并停止引用旧内容。
2. 在已经绑定的知识目录中新增文档后，Agent 能否自动纳入新文档，而不需要重新绑定。
3. 删除文档、移出绑定目录或撤销权限后，Agent 能否停止引用已经失效的内容。

完整测试步骤和记录模板见 [知识库绑定行为验证](知识库绑定行为验证.md)。判断规则如下：

| 验证结果 | 方案处理 |
|---|---|
| 三项全部通过 | 目标知识库内部变化由知识库平台负责；Skill 不扫描、不记录、不重复写回这些变化 |
| 修改未生效 | 作为索引刷新或缓存问题处理，不并入知识沉淀流程 |
| 新文档未自动纳入 | 作为目录绑定或文档注册问题处理，必要时单独建设绑定管理能力 |
| 删除后仍可引用 | 作为索引失效、缓存或权限同步问题优先修复，不能用知识提案掩盖 |

这里的“Agent 感知”是指：用户提问时，Agent 能通过知识检索返回变化后的有效内容，并提供正确来源；不要求 Agent 因文档变化而主动唤醒或发送通知。

### 2.3 两条知识变化链路

验证通过后，知识变化分为两条链路：

```text
链路 A：目标知识库内部变化
人工新增、修改或删除正式知识
→ 知识库平台更新索引
→ Agent 下次检索时使用最新内容
→ 不进入同步 Skill 和 Base 审核表

链路 B：知识库外部产生新信息
会议、妙记、Meegle、Base、上游项目文档
→ Skill 发现增量并判断是否值得沉淀
→ 生成知识提案并审核
→ 写入 Agent 已绑定知识库
→ Agent 下次检索时使用新知识
```

Skill 的核心价值是链路 B，即把分散的业务信息转化为经过审核的正式知识，而不是复制链路 A 已由知识库平台完成的工作。

### 2.4 上游采集范围与成本架构

链路 B 不对公司飞书生态做全量扫描，而是按以下优先级接收知识候选：

1. **主动投递**：人员将文档放入“待沉淀”共享目录、添加约定标签，或在知识候选 Base 中提交来源链接。
2. **专用业务视图**：读取 Base、Meegle 中的“已确认决策”“已完成复盘”“待沉淀知识”等窄视图或 MQL。
3. **受限增量扫描**：只对明确配置的会议系列、共享目录、项目、人员和关键词检查新增或修改；不得退化为全空间搜索。
4. **默认排除**：个人云空间、临时草稿、聊天噪音、全量项目状态和未授权内容默认不进入扫描。

成本控制漏斗如下：

```text
公司全部飞书内容（默认不扫描）
→ 明确授权的主动投递入口、专用视图和白名单来源
→ 更新时间、事件、目录、人员、项目、状态等元数据筛选
→ 游标、来源 ID、内容哈希和业务规则去重筛选
→ 只读取发生变化且可能相关的少量正文
→ 只将少量候选交给模型判断和提炼
→ 人工审核后写入知识库
```

运行节奏拆分为：

- 每天或由事件触发执行低成本增量发现，不批量读取全部正文。
- 每周集中审核知识候选和处理积压。
- 每月只统计效果、成本与遗漏，不重新全量扫描历史内容。
- 历史补录使用独立任务和单独预算，不占用日常运行额度。
- 多个 Agent 订阅同一来源时，进入多 Agent 阶段后应“采集一次、缓存一次、分别路由”，避免重复读取和重复消耗模型 Token。

### 2.5 动态事实与稳定知识分流

| 信息类型 | 权威来源 | 处理方式 |
|---|---|---|
| 项目状态、负责人、排期、任务进度 | Meegle | 保留在 Meegle，Agent 使用时实时读取 |
| Base 中持续变化的业务数据 | 飞书 Base | 保留在 Base，Agent 使用时实时读取 |
| 会议确认的决策和规则 | 妙记、会议纪要 | 提炼后进入审核流程 |
| 尚未进入目标知识库的品牌、产品方法论 | 上游飞书文档、Wiki | 增量更新到公共或专属目录 |
| 已稳定的项目经验和复盘 | Meegle、文档、会议 | 审核后沉淀为长期知识 |

不得把动态项目状态复制为永久知识，否则 Agent 会持续引用已经过期的负责人、排期和进度。

## 三、完整工作流

### 3.1 候选入口与数据采集

按 Agent 配置读取，但优先接收主动投递和专用业务视图：

- 会议和妙记：只检索配置的会议系列、关键词、参与人、所有者或固定妙记；先读取摘要和元数据，必要时再取完整内容。
- 上游文档：优先处理主动提交的文档或“待沉淀”共享目录；搜索必须同时限定目录和关键词，不得把公共或专属目标知识文档配置为来源。
- Base：只读取指定表中的专用视图；动态业务表不作为长期知识来源整表扫描。
- Meegle：只读取指定项目中的专用视图或 MQL；日常状态默认不进入知识提炼。

所有来源统一转换为：

```yaml
source_type: meeting | document | base | meegle
source_id: 唯一标识
source_url: 来源链接
title: 标题
owner: 所有者
updated_at: 来源更新时间
collected_at: 采集时间
content_hash: 内容哈希
content: 正文或结构化数据
```

### 3.2 低成本筛选、增量与相关性判断

执行顺序固定为：

1. 使用固定来源白名单和权限范围排除公司全空间、个人空间和未授权内容。
2. 读取来源侧变更事件、更新时间或上次成功游标，只保留新增或修改的元数据。
3. 先使用目录、视图、状态、人员、项目、关键词和排除词做无模型筛选。
4. 只有通过上述筛选的候选才读取正文；长文优先使用变更段落或摘要。
5. 通过 `source_id + content_hash` 去重，避免相同内容进入后续处理。
6. 仅对剩余少量候选做模型语义相关性判断和知识提炼。
7. 保存“为什么与该 Agent 相关”、各阶段数量和模型 Token 消耗。
8. 达到单次运行预算后停止扩大读取范围，将剩余候选安全顺延，不能简单提高上限。

当前 V2 实现与目标架构存在以下差距，必须如实区分：

- 当前同步脚本不调用大模型；相关性判断是关键词、人员和项目字符串匹配，候选正文是截取后的来源内容，尚未完成真正的语义提炼。
- 会议之外的部分来源仍会先分页读取内容，再比较批次哈希；当前去重能够避免重复提案，但不能完全避免重复读取。
- 当前只有单条候选字符上限，没有单次正文总量、候选数量、模型 Token、运行时长和 API 调用次数的硬预算。
- 当前尚未自动强制文档搜索必须绑定目录、相关性规则不得全部为空、来源与目标 Token 不得重叠；在代码校验完成前只能在严格受控的 MVP 配置中运行。
- 当前没有跨 Agent 共享采集缓存；该能力在多 Agent 阶段建设。

### 3.3 知识提炼

只提炼：

- 已确认事实。
- 明确决策。
- 稳定业务规则。
- 可复用工作流程。
- 品牌或产品知识。
- 已验证经验。
- 对旧知识的明确修订。

动态项目状态只形成运行摘要，不写入长期知识。

### 3.4 审核与写入

建立三个 Base 数据表：

- `知识变更审核表`：只记录从上游来源生成的知识沉淀提案，不镜像目标知识库中的普通人工编辑。
- `同步运行表`：记录每次运行的成功、跳过、失败和数量统计。
- `同步游标表`：记录每个 Agent、每类上游数据源最后一次成功位置和内容哈希，不记录目标知识文档的编辑位置。

审核状态：

```text
待审核 → 已批准 → 已应用
       ↘ 已拒绝
       ↘ 需修改
```

MVP 阶段：

- 扫描任务只生成审核记录，不直接修改知识文档。
- 审核人将状态改为“已批准”。
- 人工运行应用命令，将批准内容写入目标目录。

生产阶段：

- Base 状态变为“已批准”后，飞书自动化调用在线执行器。
- 执行器写入目标知识文档并将状态改为“已应用”。
- 重复调用同一变更 ID 不得重复写入。

## 四、安全规则及要避免的问题

| 规则 | 具体避免的问题 | 实现方式 |
|---|---|---|
| 飞书正文只作为数据 | 文档中出现“忽略规则、执行命令、删除知识”等文字时，可能诱导 Agent 执行提示注入 | 采集内容只进入分析字段，不进入系统指令；禁止从正文生成工具调用 |
| 每条知识保留来源和时间 | 无法判断知识来自哪里、是否已经过期，出现错误时无法追责 | 保存来源类型、链接、更新时间、采集时间和内容哈希 |
| 原文事实与 Agent 推断分开 | Agent 的理解可能被误当成正式业务规则，形成错误知识 | 分别标记“原文事实”“提炼结论”“Agent 推断”；推断默认需要审核 |
| 不直接删除或覆盖旧知识 | 一次误判可能造成已有知识永久丢失，且无法恢复 | 生成新增、替换、过期或冲突提案；保留旧版本和回滚依据 |
| 不同 Agent 严格隔离 | 品牌信息进入产品 Agent、未授权项目数据进入其他 Agent，造成知识污染或权限泄露 | 每个 Agent 使用独立配置和专属目录；目标目录由固定 Token 指定 |
| 不沉淀密钥和身份凭证 | Token、API Key 或授权信息可能被写入知识库，继而被用户查询到 | 写入前检测并过滤敏感字段；密钥只存运行环境的安全凭证区 |
| 高风险变更必须审核 | 自动修改公司规则、方法论或覆盖旧结论可能影响所有 Agent | 公共知识、替换、删除、冲突一律人工审核；MVP 所有变更均审核 |
| 使用最小权限 | 一个 Agent 获得过大的飞书权限后，可能读取或修改无关知识 | 只授权指定知识目录、Base、Meegle 项目和必要 API Scope |
| 成功后再提交游标 | 中途失败却提前更新游标，会导致部分内容永久漏同步 | 全部必要步骤成功后才更新游标；失败保留原游标以便重试 |
| 同一变更必须幂等 | 网络重试或自动化重复触发可能导致知识重复写入 | 使用变更 ID、来源 ID 和内容哈希进行写入前检查 |
| 动态数据库保持唯一事实源 | Meegle 或 Base 数据复制到文档后会快速过期，产生多个相互冲突的版本 | 动态状态实时查询；只有稳定规则、决策和复盘结论进入长期知识 |
| 审核记录不可绕过 | 人工口头同意但系统无记录，后续无法审计谁批准了什么 | 审核人、审核时间、审核意见和应用结果统一保存在 Base |
| 目标知识与上游来源不重叠 | 正式知识文档被再次扫描后，可能生成提案并写回自身，形成自循环 | 目标文档 Token 不得出现在 `sources.documents`；目标知识只用于写入校验和冲突比较 |
| 不复制知识库原生历史 | 同一编辑同时出现在飞书版本历史和审核表，增加噪声且无法说明业务价值 | 普通人工编辑沿用飞书版本历史；审核表只保存上游知识沉淀提案 |
| 不做公司级全量扫描 | 内容量、API 调用、模型 Token 和审核量会随时间快速增长，且噪音压低提案质量 | 默认拒绝全空间搜索，只允许主动投递、专用视图和明确白名单来源 |
| 个人文档默认不扫描 | 个人草稿和工作过程既可能无关，也可能包含不应跨团队使用的信息 | 仅接受主动提交、指定共享目录或负责人明确批准的个人文档 |
| 先筛元数据再取正文 | 先读取所有全文再判断相关性，会浪费调用额度、处理时间和模型 Token | 先检查事件、更新时间、目录、人员、项目、状态和规则，只为少量候选取正文 |
| 单次运行设硬预算 | 某周内容突增时可能产生不可预测的成本和审核积压 | 限制元数据数、全文数、总字符、模型 Token、提案数和运行时长；超限顺延 |

## 五、分阶段实施

### Phase 0：知识库原生感知验证

在选择同步 MVP 和配置上游来源前，先选择一个测试 Agent 与测试目录，完成三项黑盒验证：

- 已绑定文档内容修改后的生效情况和索引延迟。
- 绑定目录中新建文档后的自动纳入情况和索引延迟。
- 文档删除、移出目录或撤权后的失效情况和索引延迟。

交付：

- 一份填写完整的 [知识库绑定行为验证记录](知识库绑定行为验证.md)。
- 三项能力的真实结果、首次生效时间和证据。
- 是否将目标知识库内部变化排除出同步 Skill 的明确结论。
- 如果存在失败项，对应的索引、绑定、缓存或权限问题清单。

Phase 0 没有结论前，不进入自动运行，也不把目标知识文档配置成扫描来源。

### Phase 0.5：采集范围与成本验证

在真实业务扫描前，按 [Agent 上游采集范围与成本验证](采集范围与成本验证.md) 为首个候选 Agent 建立来源清单和成本漏斗，证明同步范围是少量、明确、可解释和可控的。

范围准入：

- 100% 来源都有业务用途、负责人和固定范围。
- 文档搜索同时配置上游共享目录和关键词；未经授权的个人文档读取数为 0。
- 会议或妙记至少配置业务关键词，并叠加参与人、所有者或固定妙记范围。
- Base 和 Meegle 的稳定知识来源使用专用视图或 MQL，不读取整库、整项目。
- 目标知识目录和目标知识文档读取数为 0。

首个 MVP 的默认单次预算如下；需要放宽时由业务负责人记录原因：

| 指标 | 默认上限 |
|---|---:|
| 元数据命中数 | 100 条 |
| 正文读取数 | 20 条 |
| 正文总字符数 | 60,000 |
| 进入模型的候选数 | 10 条 |
| 模型输入 / 输出 | 15,000 / 3,000 Token |
| 待审核提案数 | 5 条 |
| 总运行时间 | 10 分钟 |

有效性要求：准备不少于 10 条预期样例，至少发现 8 条；首轮“批准或仅需小修改”的提案不低于 60%；动态状态、未确认草稿和无关个人内容进入长期知识的数量为 0。超预算时停止继续读取并记录原因，通过缩小目录、视图、时间窗或关键词后重试。

上述硬预算、元数据优先、Token 统计和 `dry-run` 当前尚未全部由 V2 代码实现。首个 MVP 只能在隔离测试仓和严格小范围配置下验证；扩大到多 Agent 前必须完成代码级限制。

未启用模型时，Token 指标标记为“未启用”，只能先确认来源范围准入，不能以 `0 Token` 判定成本验证通过。Phase 1 接入模型后必须复测 Token、提案质量和审核通过率，完成 Phase 0.5 的成本闭环。

### Phase 1：单 Agent MVP

运行方式：本地 Codex。

交付：

- 创建公共 Skill 和配置模板。
- 创建三个 Base 管理表。
- 使用 Phase 0 结果确认目标知识库与上游来源边界。
- 使用 Phase 0.5 结果确认主动投递入口、专用视图、白名单来源和单次预算。
- 从品牌六要素或产品五张牌 Agent 中选择首个满足条件的对象。
- 在严格小范围内接入妙记、文档、Base 和 Meegle，不要求为了覆盖数据源类型而接入无真实价值的来源。
- 跑通受限采集、增量、去重、候选生成、审核和人工应用；当前规则候选与后续模型提炼的效果分开记录。
- 连续运行两次验证幂等。

MVP 选择规则：

1. 已经能够读取飞书知识。
2. 有明确负责人和审核人。
3. 已建立公共及专属知识目录。
4. 至少有一类持续变化的数据源。
5. 能准备不少于 10 条预期知识变更样例。
6. 能建立主动投递入口或至少一类专用业务视图，并确认单次运行预算。

第一个满足全部条件的 Agent 作为 MVP；如果品牌六要素和产品五张牌同时满足，默认选择品牌六要素 Agent。

### Phase 2：多 Agent 配置化

交付：

- 为多个 Agent 分别创建 `agent-sync.yaml`。
- 公共 Skill 只维护一份，Agent 不分叉代码。
- 增加公共/专属知识路由。
- 增加冲突、过期和替换检测。
- 增加来源侧增量、元数据优先、硬预算、Token 统计和 `dry-run`。
- 对多个 Agent 共用的来源增加共享采集缓存，实现采集一次、按 Agent 分别路由。
- 增加 Claude 兼容适配，但保持同一套配置结构和知识规则。
- 批量运行多个 Agent，验证数据和知识互不污染。

### Phase 3：每周自动运行

交付：

- 将相同 Python 同步核心部署为持续在线的轻量执行器。
- 飞书事件或日计划只执行低成本增量发现；每周集中审核和生成汇报。
- 飞书内自动化调用执行器时传入 `agent_id`，不得扩大服务器配置中的来源范围。
- 如果飞书自动化无法调用 HTTPS 接口，使用执行器内置周计划作为确定性后备方案。
- Base 审核通过后自动调用应用接口。
- 增加失败重试、超时、限流、运行告警和周报。
- 低风险专属知识可逐步自动批准；公共知识和覆盖性变更始终人工审核。

## 六、实施接口与验证

公共同步核心使用 Python 实现，保证本地 Codex、Claude 适配和在线执行器复用同一逻辑。

命令接口：

```text
sync scan  --config <agent-sync.yaml>
sync apply --config <agent-sync.yaml> --proposal-id <id>
sync status --config <agent-sync.yaml>
```

在线执行器接口：

```text
POST /v1/agents/{agent_id}/sync
POST /v1/proposals/{proposal_id}/apply
GET  /v1/runs/{run_id}
```

所有在线接口必须鉴权，且不得从请求正文覆盖 Agent 配置中的数据源或目标目录。

核心测试：

- 已绑定文档修改后，Agent 能否读取新内容并停止引用旧内容。
- 绑定目录新增文档后，Agent 能否自动读取新文档。
- 文档删除、移出目录或撤权后，Agent 能否停止引用失效内容。
- 首次同步能生成正确提案。
- 相同内容第二次运行不重复生成。
- 来源修改后只生成变更部分。
- 无关内容不会进入审核表。
- 恶意操作指令不会触发工具调用。
- Meegle 动态状态不会写成长久知识。
- 公共和专属知识路由正确。
- 单个来源失败时不提交该来源游标。
- 审核拒绝后不能写入知识库。
- 同一批准记录重复执行不重复写入。
- Agent A 的内容不能写入 Agent B 的目录。
- 目标知识文档不能同时作为上游文档来源。
- 个人文档未经主动提交或明确授权时不能被扫描。
- 文档搜索没有限定共享目录时必须拒绝运行。
- Base 和 Meegle 稳定来源没有专用视图或 MQL 时必须拒绝运行。
- 元数据筛选发生在正文读取和模型处理之前。
- 单次运行达到正文、候选、Token 或时间预算时安全停止并顺延。
- 同一来源被多个 Agent 使用时只采集一次、分别路由。
- 写入失败能保留提案并安全重试。

验收标准：

- 三项知识库原生感知测试均有真实结果和索引延迟记录。
- 根据 Phase 0 结果明确划分知识库平台与同步 Skill 的职责，不重复建设。
- Phase 0.5 有完整的来源范围、成本漏斗、预算和证据记录。
- 公司全空间、未授权个人文档、目标知识目录和目标文档的扫描数量为 0。
- 首个 MVP 不少于 10 条预期样例中至少发现 8 条，首轮“批准或仅需小修改”的提案不低于 60%。
- 单次运行不超过已批准的正文、候选、Token、提案和时长预算；超限内容能够安全顺延。
- 连续两次运行无重复知识。
- 每条知识均有来源、时间和审核记录。
- 所有越权、冲突、覆盖和公共知识变更进入人工审核。
- 单个来源失败不破坏其他来源和既有知识。
- 多 Agent 运行时配置、知识、游标和报告完全隔离。

## 七、当前前置条件

- 需要可用的 `lark-cli v7.0.4` 或兼容版本。
- 实施前必须完成飞书授权，并验证离线刷新。
- 使用 Meegle 前需要安装、登录并验证目标项目权限。
- MVP 使用用户身份验证业务流程；生产阶段优先使用应用身份或专用服务账号，避免依赖个人长期在线。
- 配置文件不得包含 `.env`、Token、API Key 或其他凭证。
- 现有 Agent 已能读取飞书知识，因此问答检索链路不在本项目实施范围。
- 已绑定知识库对新增、修改、删除的真实响应行为目前尚未确认，必须先完成 Phase 0 验证。
- 当前 V2 尚未实现元数据优先、单次总量与 Token 硬预算、真正的模型语义提炼、`dry-run` 和跨 Agent 共享采集缓存；必须按 Phase 0.5 和 Phase 2 的节奏补齐，不能直接扩大为公司级扫描。
